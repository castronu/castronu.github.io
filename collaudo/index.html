What I check

Every check passes or fails. If a blocking check fails, the area is red.

No.AreaGoalChecks
1Data and permissions

No user can read or change data that isn't theirs, not even by calling the database directly.

Three sample checks
  • 1.3Isolation between customers. Two users from two different customers try to read and write every table. Passes if neither sees the other's data.
  • 1.4What can be read without logging in. I call every table with the public key only. Passes if only intentionally public data comes back.
  • 1.6Where the admin role comes from. Passes if a user cannot grant it to themselves.

2Schema and migrations

The production database can be rebuilt from the repository, and every change goes through a versioned file.

Three sample checks
  • 2.1Versioned schema. I rebuild the database from scratch and compare it with production. Passes if there are no differences.
  • 2.3No manual changes. Passes if only the release pipeline applies schema changes.
  • 2.4Destructive changes. Passes if each one has a backup taken beforehand and a written rollback step.

3CI and tests

Nothing reaches production without automated checks that test behaviour.

Three sample checks
  • 3.1Permission tests. Passes if a change that exposes one customer's data to another is blocked automatically.
  • 3.3Flows that move money or data. Payment, the same notification received twice, two bookings at the same instant.
  • 3.5Secret scanning. Passes if a commit containing a key is rejected.
 8
4Environments

You can try a change without touching customer data, and roll back in minutes.

Three sample checks
  • 4.1Separate previews. Passes if no preview uses the production database.
  • 4.2External services in test mode. Passes if the test environment cannot charge a real card or message a real customer.
  • 4.4Rollback to the previous version. Tried once, timed. Passes if it takes less than 10 minutes.
 6
5Observability

A problem reaches you before a customer reports it.

Three sample checks
  • 5.1Errors tracked everywhere. I trigger a test error from the browser, the server and a scheduled job. Passes if all three show up.
  • 5.2Errors reach a person. Passes if the alert arrives within 5 minutes on a channel someone reads.
  • 5.3Monitoring from outside. Login, main functions and payments checked from outside at least every 5 minutes.
 8
6Backups, secrets and GDPR

Data can be recovered, keys don't leak, and every piece of personal data has an expiry.

Three sample checks
  • 6.1Restore tested. I restore the latest backup to a separate project and time it. A backup that has never been restored doesn't count.
  • 6.2Privileged keys. Passes if no full-access key can be reached from the browser.
  • 6.7Personal data expiry. Passes if every table has a written retention period and an automatic deletion that works.

Three sample checks

  • 7.4Destructive commands blocked. I try a forbidden command. Passes if the tool stops it.
  • 7.5Changes only with green checks. Passes if the last 20 releases all went through the automated checks.

Working days.

Five days, from access to report

The audit reads and changes nothing. You can keep developing while I work.

  1. Day 0

    Kickoff

    A 30-minute call. You give me read-only access to the repo and the database. We sign a confidentiality agreement and a data processing agreement.

  2. Days 1, 2 and 3

    Analysis

    I run the 59 checks with automated scripts and manual review. I try the permissions with test users, one per role and per customer.

  3. Day 4

    Report

    A rating for each of the 7 areas, the 10 most serious problems in order, and an estimate for fixing them. With it come the skills, the rewritten agent instructions and the ready-made tickets.

  4. Day 5

    Final call

    One hour to go through the report together. If you want to continue, you get a fixed price for the hardening.

Frequently asked questions

Do I have to give you access to production?

Read-only and time-limited. Before starting we sign a confidentiality agreement and the data processing agreement the GDPR requires. When the work is done you revoke the access.

I used Lovable. Is that still fine?

Yes, if the project is connected to GitHub. Database, permissions and backups are checked the same way as in an app written with Claude Code or Cursor.

Do I have to stop developing during the audit?

No. The audit reads code and configuration and changes nothing.

What changes for me after the hardening?

You keep building with your agent. The rules and checks stay in the repository: if a change exposes one customer's data to another, it is stopped before it reaches production.
