Chaque contrôle passe ou échoue. Si un contrôle bloquant échoue, le domaine est rouge.

1Données et permissions

Aucun utilisateur ne lit ni ne modifie des données qui ne sont pas les siennes, même en appelant directement la base.

Trois exemples de contrôles
  • 1.3Isolation entre clients. Deux utilisateurs de deux clients différents essaient de lire et d'écrire dans chaque table. Passe si aucun ne voit les données de l'autre.
  • 1.4Ce qu'on peut lire sans connexion. J'appelle chaque table avec la seule clé publique. Passe si seules des données volontairement publiques reviennent.

La base de production peut être reconstruite depuis le dépôt et chaque modification passe par un fichier versionné.

  • 2.4Modifications destructrices. Passe si chacune a une sauvegarde faite avant et une étape de retour arrière écrite.

    Appel final

    Une heure pour lire le rapport ensemble. Si vous souhaitez continuer, vous recevez un prix fixe pour le durcissement.

Ce que je ne fais pas

Questions fréquentes

Dois-je vous donner accès à la production ?

En lecture seule et pour une durée limitée. Avant de commencer, nous signons un accord de confidentialité et l'accord de sous-traitance prévu par le RGPD. À la fin du travail, vous révoquez les accès.

J'ai utilisé Lovable. Est-ce que cela convient aussi ?

Oui, si le projet est relié à GitHub. La base, les permissions et les sauvegardes se contrôlent comme pour une application écrite avec Claude Code ou Cursor.

Dois-je arrêter de développer pendant l'audit ?

Non. L'audit lit le code et la configuration et ne modifie rien.

Qu'est-ce qui change pour moi après le durcissement ?

Vous continuez à construire avec votre agent. Les règles et les contrôles restent dans le dépôt : si une modification ouvre les données d'un client à un autre, elle est arrêtée avant d'arriver en production.
