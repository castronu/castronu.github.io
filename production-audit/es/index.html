Qué reviso

Cada control pasa o no pasa. Si falla uno bloqueante, el área queda en rojo.

N.ºÁreaObjetivoControles
1Datos y permisos

Ningún usuario lee ni modifica datos que no son suyos, ni siquiera llamando directamente a la base de datos.

Tres controles de ejemplo
  • 1.3Aislamiento entre clientes. Dos usuarios de dos clientes distintos intentan leer y escribir en cada tabla. Pasa si ninguno ve los datos del otro.
  • 1.4Qué se puede leer sin iniciar sesión. Llamo a cada tabla solo con la clave pública. Pasa si solo vuelven datos deliberadamente públicos.
  • 1.6De dónde sale el rol de administrador. Pasa si un usuario no puede asignárselo a sí mismo.

2Esquema y migraciones

La base de datos de producción se reconstruye desde el repositorio y cada cambio pasa por un archivo versionado.

Tres controles de ejemplo
  • 2.1Esquema versionado. Reconstruyo la base de datos desde cero y la comparo con producción. Pasa si no hay diferencias.
  • 2.3Ningún cambio a mano. Pasa si los cambios de esquema solo los aplica el pipeline de despliegue.
  • 2.4Cambios destructivos. Pasa si cada uno tiene una copia hecha antes y un paso de vuelta atrás por escrito.

3CI y tests

Nada llega a producción sin controles automáticos que prueban el comportamiento.

Tres controles de ejemplo
  • 3.1Tests de permisos. Pasa si un cambio que abre los datos de un cliente a otro se bloquea automáticamente.
  • 3.3Flujos que mueven dinero o datos. Pago, el mismo aviso recibido dos veces, dos reservas en el mismo instante.
  • 3.5Detección de secretos. Pasa si se rechaza un commit que contiene una clave.
 8
4Entornos

Pruebas un cambio sin tocar los datos de los clientes y vuelves atrás en pocos minutos.

Tres controles de ejemplo
  • 4.1Vistas previas separadas. Pasa si ninguna vista previa usa la base de datos de producción.
  • 4.2Servicios externos en modo de prueba. Pasa si el entorno de pruebas no puede cobrar a una tarjeta real ni escribir a un cliente real.
  • 4.4Vuelta a la versión anterior. Probada una vez, cronometrada. Pasa si lleva menos de 10 minutos.
 6
5Observabilidad

Un problema te llega a ti antes de que lo avise un cliente.

Tres controles de ejemplo
  • 5.1Errores registrados en todas partes. Lanzo un error de prueba desde el navegador, el servidor y una tarea programada. Pasa si aparecen los tres.
  • 5.2Los errores llegan a una persona. Pasa si el aviso llega en menos de 5 minutos a un canal que alguien lee.
  • 5.3Vigilancia desde fuera. Acceso, funciones principales y pagos comprobados desde fuera al menos cada 5 minutos.
 8
6Copias, secretos y RGPD

Los datos se recuperan, las claves no se filtran y cada dato personal tiene una caducidad.

Tres controles de ejemplo
  • 6.1Restauración probada. Restauro la última copia en un proyecto aparte y mido el tiempo. Una copia que nunca se ha restaurado no cuenta.
  • 6.2Claves privilegiadas. Pasa si ninguna clave con plenos poderes es accesible desde el navegador.
  • 6.7Caducidad de los datos personales. Pasa si cada tabla tiene un plazo por escrito y un borrado automático que funciona.

7Agente de IA

El agente que escribe el código trabaja con los límites de un desarrollador recién llegado.

Tres controles de ejemplo
  • 7.1Ninguna clave de producción para el agente. Pasa si el agente no puede escribir en la base de datos de los clientes.
  • 7.4Comandos destructivos bloqueados. Pruebo un comando prohibido. Pasa si lo detiene la herramienta.
  • 7.5Cambios solo con controles en verde. Pasa si los últimos 20 despliegues han pasado todos por los controles automáticos.

    Una hora para leer el informe juntos. Si quieres seguir, recibes un precio fijo por el hardening.

Preguntas frecuentes

¿Tengo que darte acceso a producción?

De solo lectura y por tiempo limitado. Antes de empezar firmamos un acuerdo de confidencialidad y el acuerdo de encargo del tratamiento que exige el RGPD. Al terminar el trabajo revocas los accesos.

He usado Lovable. ¿Sirve igual?

Sí, si el proyecto está conectado a GitHub. La base de datos, los permisos y las copias se revisan igual que en una aplicación escrita con Claude Code o Cursor.

¿Tengo que dejar de desarrollar durante la auditoría?

No. La auditoría lee el código y la configuración y no modifica nada.

¿Qué cambia para mí después del hardening?

Sigues construyendo con tu agente. Las reglas y los controles se quedan en el repositorio: si un cambio abre los datos de un cliente a otro, se detiene antes de llegar a producción.
